## 0. Short answers

1. `AppLocalization` declares **762 members: 624 `val x: String` and 138 `fun f(...): String`**
   (plus the inherited `localeCode`, 763 in total). Other documents say 625 `val`: that count
   includes the extension property `LocalizationManager.Strings` on line 792, which is not a
   member. All 15 providers implement all 762 (checked by script).
2. Every `val` is a plain string literal in every provider. The `fun` members contain Kotlin
   logic (Arabic and Russian plural rules, `if`, null handling), so they cannot be turned into
   format templates: they must be **called in Kotlin**.
3. The language is one string in `settings.properties` (`language=system` or one of 15 codes).
   `AppLanguage` (a Kotlin `object`) holds the choice and a `StateFlow<String>` with the active
   code; RTL is `code in {ar, fa, ur, he}`. Compose re-creates the whole tree on a change.
4. Proposal (verified end to end): a generated Slint `global Strings` with 624 string
   properties, 138 pure callbacks behind 138 pure functions, plus `language-code`, `rtl` and
   `revision`; generated C++ glue; generated Kotlin table with **two** exported C functions.
   A language switch is one call into Kotlin and 624 property sets: **0.36 ms** measured.
   Memory for the whole feature: about **0.7 MB private bytes**.
5. A pure callback alone does **not** refresh when the language changes (verified: the text
   stayed English). The generated wrapper function passes `revision` to the callback, and that
   makes every use refresh (verified).
6. Slint 1.18.1 has no layout mirroring. RTL has to be written in `.slint` with `Strings.rtl`.

## 3. Language: chosen, stored, changed, observed

### 3.1 The library (`LIB/LocalizationManager.kt`)

- State (plain `var`, no lock, no flow): `supportedProviders: MutableMap<String,
  LocalizationProvider>` (key = `localeCode.lowercase().replace("_", "-")`),
  `defaultLanguage: String?`, `currentSelectedLanguage: String = getSystemFullLocale()`
  (line 8, evaluated when the object is first used), `currentProvider`.
- `registerProviders(vararg)` (17-23), `setDefaultLanguage(code)` (11-15; it also **sets the
  current language to the default**), `changeLanguage(code)` (25-39: exact code, else the part
  before `-`, else the default, else the first provider), `getCurrentLanguage()` (41),
  `getProvider<T>()` (52-59, unchecked cast; throws `IllegalStateException` when nothing is
  registered).
- Not observable and not thread-safe: call it from one thread (section 5.6).

### 3.2 `LocalizationStart.kt`

```kotlin
val appLanguages: List<AppLocalization>                      // 25-41, the 15 objects
fun LocalizationManager.start()                              // 45-57
object AppLanguage {                                         // 59-77
    const val SYSTEM = "system"
    private val rtl = setOf("ar", "fa", "ur", "he")
    val current: StateFlow<String>                           // starts as "en"
    var choice: String = SYSTEM   (private set)
    val isRtl: Boolean get() = _current.value.substringBefore('-') in rtl
    fun change(choice: String)
}
```

- `start()`: guarded by a private `started` flag (runs once); `registerProviders(*appLanguages
  .toTypedArray())`, `setDefaultLanguage("en")`, then
  `AppLanguage.change(runCatching { AppSettingsRepository().loadSettings().language }
  .getOrDefault("system"))`. It therefore needs `PathResolver` (one of the mingwX64 `actual`s
  still to write).
- `AppLanguage.change(choice)` (72-76): `choice` is kept only when it equals a provider's
  `localeCode` exactly, otherwise it becomes `"system"`; then
  `LocalizationManager.changeLanguage(if (system) getSystemFullLocale() else choice)` and
  `_current.value = LocalizationManager.getCurrentLanguage()`. Result: `current` is always one
  of the 15 codes (an unsupported system language gives `en`).
- `getSystemFullLocale()` on mingwX64 (`desktopNative/kmpLocalization-mingw/
  getSystemFullLocale.mingw.kt`): `GetUserDefaultUILanguage` -> `LCIDToLocaleName`, else
  `GetUserDefaultLocaleName`, else `"en"`. **Verified:** returns `en-US` on this PC. The JVM
  actual is `Locale.getDefault().toLanguageTag()`. Not compared on a Windows whose display
  language is not English.

### 3.3 Storage

- File: `<settings directory>/settings.properties`, key `language`

### 3.5 RTL

- Decided only by `AppLanguage.isRtl` (`LocalizationStart.kt:62,70`): active code before `-`
  in `{ar, fa, ur, he}`. Shipped RTL languages: `ar`, `fa`.
- `isRtl` is a plain getter, not a flow: read it after `current` emits.
- Compose applies it once at the root (`UI/App.kt:181-185`), which mirrors every `Row`, every
  start/end padding and alignment, and text alignment. Dialogs are separate windows in Compose
  but inherit the composition local.
- Numbers and sizes inside RTL text are protected by `ltr()` (section 4.2).

## 4. `localizeStep` and `ltr`

### 4.1 `localizeStep(text: String): String` (`I18N/start/StepText.kt`)

Why it exists: the engines write status texts in English (`currentStepText`, `speedText`,
`postProcessLabel`, `errorMessage`, torrent states, `ytDlpStatus`, `torrentEngineStatus`),
these are also saved in `tasks_cache.json`, and code compares them (for example
`startsWith("Step")`, `startsWith("Merging")`). They are translated only when shown.

Algorithm (lines 7-38):

1. Blank text is returned as it is.
2. The text is split on `" · "` (`SEPARATOR`, line 14); every part is translated on its own and
   the parts are joined with `" · "` again.
3. In a part: trim, remove a trailing `...` or `…` (regex `\s*(\.\.\.|…)$`), translate the
   core, and add `…` back when there was one. **An unknown core returns the part unchanged**
   (English).

Use in components: `text: Strings.home-add-download;`,
`text: Strings.home-selected-count(root.selected-count);`,
`horizontal-alignment: Strings.rtl ? right : left;`.

Rules:

- The main file must re-export it (`export { Strings }` in `app.slint`), otherwise C++ cannot
  reach it.
- Properties are `in` (written by C++, read by `.slint`). The defaults are the English texts,
  so the Slint preview and a build without the DLL show real texts. Callbacks have no default
  handler: before `fj_strings_bind` runs they return `""` (**verified**).
- `.slint` code calls the function (`Strings.home-sort-by(x)`), never the `fn-` callback.
- **Why the `revision` argument (verified):** a binding is re-evaluated when a property it
  read changes. A callback handler is not a property, so
  `text: Strings.fn-home-selected-count(0, n)` kept the English text `3 selected` after the
  language changed to each of the other 14 languages; it changed only when `n` changed. The
  wrapper reads `Strings.revision`, which C++ increments after every language change, so
  `text: Strings.home-selected-count(n)` showed `تم تحديد 3 عناصر`, `3 sélectionnés`, ... at
  once.
- **Every top-level component has its own instance of the global.** The Slint reference says
  a window and a `SystemTrayIcon` exported next to it "each hold their own instance". The
  prototype has `export component Tray inherits SystemTrayIcon` and
  `export component AppWindow` (`desktopNative/ui/app.slint:27,410`): bind and apply the
  strings for both (`ui->global<Strings>()` and `tray->global<Strings>()`), and for any other
  window created with `::create()`.
- Type mapping: `String` and `String?` -> `string` (`""` = null), `Int` and `Int?` -> `int`
  (negative = null; the only case is a percentage), `Boolean` -> `bool`. Slint `int` is 32-bit,
  the same as Kotlin `Int`; no `Long` exists in the interface.

### 5.4 Naming rules

1. Kotlin camelCase -> Slint kebab-case: insert `-` between a lower-case letter or digit and an
   upper-case letter, between an upper-case run and an upper-case letter followed by a
   lower-case letter, and between a letter and a digit; then lower-case.
   `homeAddDownload` -> `home-add-download`, `homeAtATime` -> `home-at-a-time`,
   `clipFirst15Min` -> `clip-first-15-min`, `fullThenCutLine1` -> `full-then-cut-line-1`,
   `stepConvertingToMp3` -> `step-converting-to-mp-3`, `sysYtDlpVersionReady` ->
   `sys-yt-dlp-version-ready`.
2. In Slint `-` and `_` are the same character in identifiers. C++ accessors use `_`:
   `set_home_add_download(...)`, `get_home_add_download()`, `on_fn_home_sort_by(...)`,
   `invoke_home_sort_by(...)`.
3. A member whose kebab name is a Slint keyword or type name, or one of the three fixed names
   (`language-code`, `rtl`, `revision`), gets the suffix `-text`. The reserved list is in
   `list_strings.py` (`SLINT_RESERVED`, `SLINT_TYPES`, `SLINT_FIXED`). **Today no member needs
   it and no two members collide** (`--names` prints `renamed: none`, `collisions: none`).
   Names that look risky but are fine as members of a global (compiled with slint-compiler
   1.18.1 without a warning): `ok`, `cancel`, `close`, `save`, `delete`, `remove`, `open`,
   `copy`, `retry`, `pause`, `resume`, `apply`, `reset`, `yes`, `no`, `back`, `done`,
   `language`.
4. A parameter whose kebab name is a keyword or type name gets the suffix `-arg`. Today:
   `percent` -> `percent-arg` (6 functions) and `duration` -> `duration-arg` (4 functions).
   Other parameter names used as they are: `n`, `count`, `name`, `time`, `start`, `end`,
   `total`, `selected`, `version`, `format`, `file`, `page`, `is-audio`, ...
5. Callback = `fn-` + member name. The prefix cannot collide: no member starts with `fn`.
6. Kotlin side: `STRING_VALUE_COUNT` (624) is generated; C++ walks the blob in the same order.

### 5.6 Generated C++ (`strings_glue.h`) and the language change

```cpp
struct FjStringsApi
{
    char *(*values)() = nullptr;
    char *(*call)(int, int, int, const char *, const char *) = nullptr;
    void (*release)(char *) = nullptr;
};

inline void fj_strings_apply(const Strings &s, const FjStringsApi &api);   624 x s.set_xxx(next()), then revision + 1
inline void fj_strings_bind(const Strings &s, const FjStringsApi &api);    138 x s.on_fn_xxx(lambda)
```

One generated handler:

```cpp
s.on_fn_details_clip_chip([api](int, slint::SharedString s0, slint::SharedString s1, bool i0) {
    return fj_strings_take(api, api.call(64, i0 ? 1 : 0, 0, s0.data(), s1.data()));

```

The header must be included after the Slint-generated header (it uses the class `Strings`).

Start-up order in the host:

1. Load `fjcore.dll`, start the core (`LocalizationManager.start()` runs inside and applies the
   saved language).
2. `auto ui = AppWindow::create(); auto tray = Tray::create();`
3. For each: `fj_strings_bind(x->global<Strings>(), api)`, set `language-code` and `rtl`,
   `fj_strings_apply(x->global<Strings>(), api)`.

Language change at run time:

1. Settings page in Slint -> callback with the chosen code (`"system"` or a code) -> C++ ->
   the bridge sends `OnLanguageChanged(choice)` to the view model (`AppLanguage.change` + save,
   unchanged Kotlin).
2. Kotlin reports "strings changed" (a collector on `AppLanguage.current`, or the event call
   returns it). The host handles it **on the Slint thread** (`slint::invoke_from_event_loop`
   when the notification comes from another thread).
3. On the Slint thread, for the window and the tray: set `language-code`, set `rtl`,
   `fj_strings_apply(...)`. Setting the 624 properties marks every binding that reads them;
   `revision + 1` marks every binding that uses a `Strings.function(...)`. Slint re-evaluates
   them lazily for the next frame.
4. Kotlin sends again every section that carries tier C text (rows, details, chrome, settings
   summaries, update, open dialogs), because those strings were built in the old language.
5. The window title (`"FetchJet - " + Strings.desktop-window-tagline`) and the tray texts are
   plain bindings on `Strings`, so they follow by themselves.

Threading: `LocalizationManager` and `AppLanguage.choice` are unsynchronized. `fj_strings_call`
runs on the Slint thread (bindings are evaluated there); `AppLanguage.change` must not run at
the same moment on another thread. Simplest rule: language events are executed on the Slint
thread, or the bridge serializes them with the strings calls (open question 3 links to
question 4 of `PORT/03-presentation-surface.md`).

### 5.8 RTL in Slint

- Contract: `Strings.rtl` (bool, set together with the strings) and `Strings.language-code`.
- Slint 1.18.1 has no layout direction switch (checked in the reference pages saved in
  `E:/tools/probes/slint-caps/docs`: only `TextHorizontalAlignment.start/end`, which follow the
  direction **of the text**, and `FlexboxLayout`'s `row-reverse`). Each mirrored place is
  written in `.slint`:
    - rows: `FlexboxLayout { flex-direction: Strings.rtl ? row-reverse : row; ... }`
      (compiles with slint-compiler 1.18.1, see `E:/tools/probes/i18n/rtl/rtl.slint`; not
      rendered here), or an `if Strings.rtl` / `if !Strings.rtl` pair for small rows;
    - explicit positions: `x: Strings.rtl ? parent.width - self.width - 8px : 8px;`;
    - text: `horizontal-alignment: Strings.rtl ? right : left;` for labels that must follow the
      UI direction (file names and URLs stay left-to-right);
    - paddings: swap `padding-left` / `padding-right` with the same condition;
    - directional icons (back arrow, chevrons) flipped by the same flag.
- Recommended: two or three small shared components (`DirRow`, `DirText`) so the condition is
  written once. Their design belongs to the UI documents (`PORT/04` .. `PORT/09`).
- `ltr()` texts keep their isolates when they pass through Kotlin; nothing to do in Slint.

## 8. Risks

1. A binding that calls the raw `fn-` callback, or a C++-set text that is not re-sent, stays
   in the old language after a switch. Rule: `.slint` uses only `Strings.<function>`; tier C
   sections are all re-sent.
2. Forgetting the second global instance (tray, any extra window) leaves that part English (its
   defaults) with empty function results.
3. Kotlin/Native C-API export bloat (5.7): +8 MB of DLL and a 1.9 MB header if the providers
   are public in the module that builds the DLL.
4. Generated files out of step (Slint, C++, Kotlin from different versions of the interface):
   wrong text in the wrong property, silently. Generate all three in one build step and add
   `STRING_VALUE_COUNT` as a run-time check in C++ (count the separators once in debug builds).
5. `LocalizationManager` is not thread-safe; a language change racing with a `fj_strings_call`
   on the Slint thread can read a half-updated state.
6. Slint has no layout mirroring: RTL is manual work on every screen and easy to miss in one
   place. Bidi rendering of mixed Arabic / Latin text and of the `ltr()` isolates was not
   looked at in a real window.
7. Fonts: Arabic, Persian, Hindi, Chinese, Japanese and Korean need glyphs; whether Slint's
   renderer falls back to Windows system fonts for them was not checked here (font topic of
   the Slint capability probe).
8. A new string still needs all 15 providers (Kotlin compile enforces it) and now also a
   regeneration; a member with a new parameter type (`Long`, a list) stops the generator until
   a rule is added.

## 9. Open questions

1. Does Slint 1.18.1 draw U+2066 / U+2069 as invisible isolates, and does it shape and order
   Arabic / Persian correctly with the chosen font? Needs one visible window (not allowed in
   this task).
2. Build wiring: generate at build time with Python (CMake + Gradle `Exec`) or commit the
   three generated files with a stale check?
3. Which thread runs `OnLanguageChanged` in the native bridge (same question as number 4 in
   `PORT/03-presentation-surface.md`); it decides whether a lock is needed around the strings
   calls.
4. Should the English words of `formatLocalSchedule` (`today`, `tomorrow`, `in N days`) and
   `AM` / `PM` be translated in the native app, or stay as in the Compose app?
5. Export all 762 members, or leave out the 107 + 42 logic-only and 28 unused ones? Measured
   saving would be below 100 KB of memory, so the default is "all".
